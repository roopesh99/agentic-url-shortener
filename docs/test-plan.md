# Test plan

_14 cases: all six ClickDeletionRaceTest scenarios, lock-acquisition and verified-wait ordering, failure guards, retained outcomes, and deterministic bounded coordination._

| Id | Covers | Level | Check |
|---|---|---|---|
| TC-FR1-01 | FR1, FR2, FR4, NFR1, NFR2 — click then delete | integration | In the running Spring context, confirm the first click operation has returned from acquiring the target link row lock and recorded its H2 session before launching deletion. Before releasing the first transaction, observe the deletion session blocked by that session on the target row lock. Release promptly after verification; confirm the existing click-count and deletion/tombstone assertions pass. |
| TC-FR1-02 | FR1, FR2, FR4, NFR1, NFR2 — delete then click | integration | Confirm the first deletion operation has acquired the target link row lock and recorded its H2 session before launching the click. Before release, observe the click session blocked by that session on the same target row lock. After release, confirm the existing deletion, click-erasure, and NOT_FOUND assertions pass. |
| TC-FR1-03 | FR1, FR2, FR4, NFR1, NFR2 — click then expiry change | integration | Confirm the first click operation has acquired the target row lock and recorded its H2 session before launching the expiry change. Before release, observe the expiry-change session blocked by that session on the same target row lock. After release, confirm the existing click-count and expiry-value assertions pass. |
| TC-FR1-04 | FR1, FR2, FR4, NFR1, NFR2 — expiry change then redirect/click | integration | Confirm the first expiry-change operation has acquired the target row lock and recorded its H2 session before launching the redirect/click operation. Before release, observe the second operation blocked by that session on the same target row lock. After release, confirm the existing expiry and redirect-status/click assertions pass. |
| TC-FR1-05 | FR1, FR2, FR4, NFR1, NFR2 — delete then expiry change | integration | Confirm the first deletion operation has acquired the target row lock and recorded its H2 session before launching the expiry change. Before release, observe the expiry-change session blocked by that session on the same target row lock. After release, confirm the existing deletion/tombstone and expiry assertions pass. |
| TC-FR1-06 | FR1, FR2, FR4, NFR1, NFR2 — expiry change then delete | integration | Confirm the first expiry-change operation has acquired the target row lock and recorded its H2 session before launching deletion. Before release, observe the deletion session blocked by that session on the same target row lock. After release, confirm the existing expiry and deletion/tombstone assertions pass. |
| TC-FR3-01 | FR3 — second operation completes before verified lock wait | unit | Provide the wait guard with a completed second-operation result and no verified target-row-lock observation. Assert that it reports test failure, does not mark the interleaving as verified, and does not permit the holder to commit as a successful race. |
| TC-FR3-02 | FR3 — bounded lock-wait observation timeout | unit | Provide the wait guard with no verified lock-wait observation through the configured deadline. Assert that it fails rather than passing or waiting indefinitely, and that its diagnostic includes the target, relevant session IDs, observed statements, and second-operation completion state. |
| TC-FR3-03 | FR3 — failure-path cleanup | unit | For early-completion and observation-timeout failures, assert cleanup releases the first-operation holder and marks its transaction rollback-only; assert the failure path cannot commit without a verified-wait condition. |
| TC-NFR1-01 | NFR1, FR1, FR2 — coordination is observation-driven | integration | Run a race scenario with the H2 lock-wait observer. Assert that the second operation is launched only after the first-lock signal and that the first transaction is released only after metadata confirms the second session is blocked by the recorded first session on the target row. No fixed sleep is used as proof of either event. |
| TC-NFR2-01 | NFR2, FR3 — bounded waiting and completion | integration | With lock contention withheld, assert the race test terminates at the configured bounded observation deadline with a diagnostic rather than hanging. With contention observed, assert the holder is released immediately after verification and both operation-completion waits are bounded. |
| TC-FR4-01 | FR4 — no production changes and existing behavior regression | integration | Run LinkStatsTest, LinkExpiryUpdateTest, LinkLifecycleTest, ClickFailureIsolationTest, and RedirectLatencyTest. Assert their existing click counting/erasure, expiry, redirect/tombstone, failure-isolation, and redirect-path behavior remains passing; verify the change is confined to the race-test harness. |
| TC-FR2-01 | FR2, FR3 — observer identifies the correct blocker and target | integration | During a race scenario, inspect the H2 session observation and assert the blocked session is the launched second operation, its blocker is the recorded first-operation session, and its executing lock-wait statement is associated with the same target link. An unrelated blocked session or query must not satisfy the wait condition. |
