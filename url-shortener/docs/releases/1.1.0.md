## Residual risks

- **The specification uses the placeholder route `/links/{linkId}`, while the approved API definition and implementation use `/api/links/{code}`.**: The requirements retain the service’s existing base path, and the documentation records the naming discrepancy. Keep the OpenAPI definition as the client-facing reference and verify clients use the implemented route.
- **Expiry updates persist in the existing column. Rolling back application code will not restore the prior expiry values, and this change does not introduce expiry-change history.**: Treat persisted user-selected expiries as valid state during rollback. If a particular value must be restored, use an operational source of truth or backup and restore it deliberately rather than reverting the database wholesale.
- **No numeric redirect-latency target was specified, so the existing latency regression test cannot establish an unstated performance threshold.**: The change avoids modifying redirect resolution, and the established `RedirectLatencyTest` is included in the full passing suite. Define and monitor a numeric target separately if one is required.

## Rollback plan

If release issues require rollback, redeploy the previous application version. No database migration or schema rollback is required; the previous version continues to use the existing `expires_at` column. The PATCH route will no longer be available, but expiry values already written remain persisted and continue to be interpreted by the existing redirect behavior. Do not automatically revert those values; restore a particular prior expiry only when required, using an operational source of truth or backup.
